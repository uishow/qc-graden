## AI 管家支持自然语言录入材料清单（用户 2026-10-15）
新增 `tryParseIntakeMaterial` + `_handleIntakeMaterial`：识别「录入/添加/记一笔/登记/加一笔」+ 材料名 + 数量 + 单价/总价，**不走 LLM** 直接 `write.insert('materials', projectId, ...)`，让 LLM 未配置时也能录入。

解析覆盖：
- 数量：阿拉伯 + 中文（一/二/两/三/四/五/六/七/八/九/十）
- 单位：个/张/件/块/套/片/根/米/条/箱/包/盒/双/对/扇/台/把/只/卷/桶/本/平方/平米
- 单价 4 模式：①`(单价)?数字(元)?[/一每]?单位` ②`每单位数字` ③裸 `数字元` ④ `共/一共/总共/合计/总价/花了 数字元` → 总价 ÷ 数量

**踩坑归纳（写 README 时中文 NP 解析通用易踩）**：
1. **head 正则不要强制 `\s+` 分隔符**：「录入材料清单，欧派木门...」中文逗号「，」紧跟正文无空白会整句不匹配。让 head 只匹动词+材料后缀，前导标点交给 body 端 `replace(/^[\s，,：:、]+/, '').trim()` 处理

## 【战略】用户提问：AI 问答周而复始出 bug，如何彻底解决（2026-10-15 21:37）

用户（非技术、单人测试）提出：每次问答都出不同的问题，截图→修→再出新问题，循环不止；
且将来多人使用会有千奇百怪的说法。此前我说过"不是模型训练的问题"，需要给出准确解释和彻底解。

**根因结论（两类要分开）**：
- A 类·理解类（结构性）：AI 管家的"理解"是手写正则规则（detectIntent / tryParse* / _routeQuery /
  _pickDiaryByText / _matchStageIds）。中文表达近乎无限、规则有限 → 每来一种新说法就是一个新 bug；
  每补一条规则还带来回归风险（「块」是钱还是量词、alternation 顺序吃字）。**不是再修几次就会好**。
- B 类·实现回归类（与 AI 无关）：按钮漏渲染、snapshot/raw id 映射丢失、快照卡恒显示"尚未设置"、
  amtRe 吃字等 —— 是测试缺口，靠回归测试可压住。
- 澄清"不是模型训练的问题"：**模型不用训练**（现成大模型够用），但**架构把模型放错位置**：
  规则在前扛、模型只在规则失败时兜底 = 用有限规则挡无限表达。应反过来。

**彻底解三层（已向用户提出）**：
1. 架构层：LLM 优先做"理解"，规则降级为①离线兜底 ②结果校验修复（repairExtract 已建）；
   写入必经预览卡+修改表单（Phase1/3 已建）→ 理解错也不落脏数据；
   读/查询类查不到就给"选择器列表"，**绝不让 AI 编理由**（AI 看不到附件本体，"图片已过期"最伤信任）。
2. 数据层（应对多人使用）：每条回复加 👍/👎 埋点，👎 落 {原话,理解结果,回复} 到反馈集合；
   按频次排序 → 无限说法收敛成"Top N 高频"，修一个覆盖一大片。**唯一能把无限变有限的机制**。
3. 工程层：每次修 bug 必须补一条回归用例；**当前 harness 在 /tmp/ai_harness.js（87 项）会丢，必须入库**。

**三条底线（现实预期）**：不写脏数据 / 不卡死不静默失败 / 不确定就说不确定并给选项、绝不编造。
做到这三条后剩余都是"理解不准"，用户改一下即可，不污染数据。

推荐优先级：① 语料入库+回归约定（0.5天）→ ② 👎反馈闭环（1-2天）→ ③ 录入改 LLM 优先（1天+部署）→ ④ 查询统一选择器。

## 反馈闭环"记下来之后如何处理"的运营设计（2026-10-15 22:14 用户提问，待确认）
核心：反馈不是用来"看"的，是用来**排序 + 分流**的。同样问题合并计数 → 按次数修 → 修完进回归语料。
- 采集：只一个 👎（不填表，否则反馈率极低），可选补一句"你期望的结果"。
- 存字段：原话 / AI理解(意图+字段) / AI回复 / 是否降级 / 项目ID / 时间 / 状态 / 处理备注 / 出现次数。不记身份。
- 后台列表：按出现次数倒序 + 状态筛选（待处理/已修/已忽略/非缺陷）。
- 处置分流：A 理解错（补规则或调 prompt + 原话进测试语料，我处理）；
  B 数据/权限类（跨项目查不到、没存附件、字段缺失）→ 产品缺陷，单独排队给你决策；
  C 期望超出能力（要的功能没接口）→ 记成需求，不是 bug。
- 节奏：每周 30 分钟，我拉 Top20 → 判定 A/B/C → A 类直接修并补用例 → B/C 整理成需求清单。
- 度量（判断是否真变好）：👎 率、Top10 占失败的比例、平均修复周期。
- 两个坑：别让用户填表；别只收集不处置（会变垃圾场，必须有状态机）。
