│  └── app.js（wx.cloud.init + 静默登录）        │
└──────────────┬──────────────────────────────┘
               │ 微信云开发 SDK（wx.cloud.*）
┌──────────────▼──────────────────────────────┐
│  微信云开发 CloudBase（env: cloudbase-d0gcanr6v1194af27）│
│  ├── 云函数 login   微信静默登录 → OPENID       │

**设计决策与理由**：

- **为什么微信原生而非 uni-app**：无跨端计划，原生对云服务 SDK、托管发布链路、隐私清单都是零摩擦路径，调试少一层编译转换。
- **为什么从 WorkBuddy 云服务改走微信云开发**：见 §0 A2 与选型评估（docs/后端云服务选型评估-2026-10-06.md）。核心结论——WorkBuddy 云服务免费额度（5000 点/月）在基准场景下约 129% 超出，决定性成本项是文档库按 5 分钟窗口计费的 PG 实例；微信云开发免费额度对「低频写、偶发读」的装修日记场景更友好，且前端 SDK 与发布链路一体。
- **为什么做数据层适配层（utils/cloud.js）而非逐页改 SDK**：把 13 个页面的数据访问收敛到唯一云边界。页面代码维持 supabase 风格链式调用（`from().select().eq().in().order().insert().update()`），适配层负责「`id`↔`_id` 映射、结果行补 `.id`、乐观锁冲突检测、存储签名 URL 映射」。迁移风险最低、可回退（详见 docs/迁移部署runbook.md）。
- **为什么同步采用「进入页面拉取」而非实时推送**：云开发数据库实时监听（watch）在小程序端可用但与文档型 + 安全规则的组合需运行时验证；V1.0 退化为「onShow 全量拉取 + 乐观锁防并发写冲突」，简单可靠，后续可平滑升级为 watch 增量。
- **为什么所有写操作带 version 乐观锁**：多人同时编辑同一篇日记是真实场景（夫妻同时记账）。云开发无内置乐观锁，由适配层 `update(o).eq('id',x).eq('version',v)` + `stats.updated===0` 实现等价冲突检测，冲突时前端弹「内容已被他人修改」提示。
- **LLM（V1.3 知识库问答 / 日记周报摘要）**：微信云开发不内置 LLM，V1.0 不阻塞；V1.3 通过云函数调用带密钥的外部 LLM（如 WorkBuddy 云服务 LLM 接口）实现，密钥仅在云函数侧，不下发前端。

## 4. 数据模型定义（微信云开发 CloudBase · 文档型）

> 约定（与 `utils/cloud.js` 及已实现代码一致）：
> - 主键 `_id`：云开发文档型自动生成的字符串，前端无感使用 `.id`（适配层在读取结果补回 `.id = _id`）。
> - 字段命名 **snake_case**（如 `project_id`、`owner_id`、`image_paths`），与原 supabase 设计文档的 camelCase 不同，以匹配小程序端实际代码。
> - 用户身份 = **openid**：来自 `login` 云函数 `getWXContext().OPENID`；前端 `app.globalData.user.id = openid`。不再有 `auth.uid()`。
> - 金额一律**整数分**存储，展示层 `fen2yuan` 格式化；`version` 为整数乐观锁。
> - 时间字段 `created_at` / `updated_at`（ISO 字符串），由代码在写操作时显式维护；客户端 SDK 创建的文档云开发会自动加 `_openid`（= 创建者 openid，安全规则据此判写权）。
> - 软删用 `deleted: boolean`；协同追溯写 `revisions`。

### 4.3 数据隔离与安全模型（微信云开发）

> 原 supabase 的 RLS 策略，在云开发下改为「安全规则 + 乐观锁」组合，详见 `docs/云开发安全规则.md`。

- **读**：业务集合全部用户可读；前端只用 `currentProjectId`（来自本人 `members` 记录）拉取，靠 `project_id` 做应用层隔离。
- **写（创建者可写）**：客户端 SDK 创建的文档自动带 `_openid`，安全规则 `doc._openid == auth.openid`。`profiles` / `knowledge_categories` / `knowledge_articles` 写权限收为 `false`（仅云函数写）。
- **乐观锁**：`update(o).eq('id',x).eq('version',v)`，命中 `stats.updated === 0` 时适配层返回 `conflict`，前端弹「内容已被他人修改」。`utils/cloud.js` 实现。
- **用户身份**：openid（login 云函数），不依赖任何 auth 表。
- **协同编辑权衡（已拍板 V1.0）**：当前「创建者可写」下，非创建者不能改他人日记。V1.0 交付「多人各自记录」；真正的多人改同一篇推迟到 V1.1，改走 `writeRecord` 云函数做「项目成员」校验后放开互改。
- **角色细粒度（owner/editor/viewer）**：V1.0 仅 `owner` 实际写入 `members`；editor/viewer 与「viewer 拒绝写」的强约束需 V1.1 `writeRecord` 落地。V1.0 前端隐藏按钮属体验层，非安全边界。

## 5. 知识库内容集成方案（官方常识预置 + ima 共享库笔记链接导入）

### 5.0 知识库分层模型

| 层 | 内容来源 | 可见范围 | 写入方式 |
|----|----------|----------|----------|
| 官方预置库 | ima「装修小常识」批量整理 | 全小程序用户只读 | 运维脚本导入（§5.2） |
| 项目共享库 | **成员在同一个 ima 共享知识库中共同记录的笔记（含现场图），经分享链接导入** | 本项目成员 | 导入页写入（§5.3），贡献者/owner 可删 |
| 公共广场（V1.x 可选） | 项目共享中被推荐的内容 | 全小程序 | owner 推荐 + 运营审核，M3 后评估 |

> 核心机制：**ima 共享知识库是全员共建的主战场**——日常随手记录、互相补充都发生在 ima 侧；小程序端不重复造一套协同编辑，而是通过「链接导入」把共享库中经过检验的笔记**精选沉淀**进项目知识库，与日记、阶段、花费产生上下文关联。导入语义是「快照沉淀」而非双端同步（见 §5.3）。

### 5.1 官方预置：三条路径对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **A. 离线结构化导入** | 从 ima 整理条目 → 标准 JSON → 一次性导入 `knowledge_articles`，定期补录 | 稳定、检索快、可离线、无外部依赖 | 内容更新需手动批次 | ✅ **MVP 采用** |
| B. 实时检索网关 | ima 若开放 API/MCP，搜索时透传查询并缓存结果 | 内容始终最新 | 依赖 ima 接口可用性与稳定性 | 预留，验证后启用 |
| C. web-view 跳转 | 文章详情跳 ima 分享页 | 实现最简单 | 体验割裂、无法检索 | 仅兜底，不做 |

### 5.2 官方预置导入管道（方案 A）

```
ima「装修小常识」
   │  ① 人工/半自动整理（标题、正文、来源备注）
   ▼
knowledge_seed/*.json   （每篇一个文件，schema 同 §4.2 knowledge_articles）
   │  ② 导入脚本：校验 schema → 去重（标题哈希）→ 写入云数据库
   ▼
knowledge_articles 集合  →  小程序只读检索
```

- JSON 必须含 `categoryId`（映射到 7 个预置分类）与 `tags`（≤5 个，用于交叉检索）。
- 去重键：`sha1(title)`，重复条目跳过并记录日志。
- 导入通道是**一次性运维脚本**，不走小程序前端；前端无写入口。

### 5.3 ima 共享库笔记 → 链接导入流程

```
全员在 ima 共享知识库中共同记录、补充装修笔记
   │  ① ima 内对笔记点「分享」→ 复制链接（或分享到微信会话）
   ▼
小程序 pages/knowledge/import
   │  ② 粘贴链接（或从分享卡片带入口令）
   │  ③ 解析链接 → 拉取标题/正文（§5.4 三级策略）
   ▼
预览编辑页：确认分类（默认按关键词建议）、标签、摘要，可修改正文
   │  ④ 确认导入 → 写 knowledge_articles
   │     （scope=shared, projectId=当前项目, contributorId=导入人,
   │       sourceLink=ima 链接, linkHash=sha1(链接)）
   ▼
项目共享库立即可见；时间线可发动态「xx 导入了一篇笔记」（可选）
```

- **分工边界**：ima 共享库负责「日常共建」（快、随意、可反复改）；小程序知识库负责「精选沉淀」（带分类标签、可与施工阶段/花费对照检索）。导入是一个**主动的精选动作**，不是自动全量同步——避免把共享库里的半成品笔记灌进项目。
- **去重**：按 `linkHash` 判重，重复导入提示「xx 已于 X 日导入过该笔记」。
- **快照语义**：导入即拍照存档，ima 源笔记后续更新**不回溯同步**——避免双端一致性问题；V1.x 如有需要再加「重新同步」按钮。
- **权限**：editor 以上可导入；导入人（contributorId）与 owner 可编辑/删除导入条目（§4.3）。
- **分享卡片直达**：支持将 ima 分享内容通过小程序卡片参数带入导入页，省掉粘贴动作（取决于 ima 分享形态，见待确认 Q4）。

### 5.4 链接解析的三级策略（按 ima 实际能力降级）

| 级 | 策略 | 前提 | 体验 |
|----|------|------|------|
| P1 | ima 开放 API/MCP：凭链接换取结构化内容 | ima 提供开放接口 | 全自动 |
| P2 | 服务端抓取公开分享页（H5）→ 正文抽取 | 链接免登录可访问 | 全自动，需防页面结构变动 |
| P3 | **手动补全**：解析失败或仅得标题时，用户从 ima 复制正文粘贴 | 总是可用 | 半自动，兜底 |

> 落地顺序：开发期先在 ima 实际分享一篇笔记，验证链接形态（H5 还是 ima 自家小程序卡片、是否免登录可见），据此决定 P1/P2 可行性；**P3 兜底必须实现**，保证任何情况下功能可用。导入页 UI 按「解析中 → 预览编辑」单流程设计，三级策略对用户透明。

### 5.5 检索规格

| 能力 | 实现 |
|------|------|
| 分类浏览 | 顶部 7 分类横滑，选中过滤 `categoryId` |
| 关键词搜索 | 对 `title / summary / content` 做包含匹配；搜索词与分类条件叠加（AND） |
| 标签 | 文章卡片可点标签，跳转同标签列表 |
| 排序 | 默认相关度（标题命中 > 摘要 > 正文），可切「最多阅读」 |
| 来源筛选 | 文章流支持「官方预置 / 成员导入」筛选；导入条目卡片展示贡献者头像与昵称 |
| 埋点 | 详情页打开时 `viewCount + 1`（节流：同用户同文章 24h 计一次） |

### 5.6 架构预留（ima API 直连 / V1.3 AI 问答）

- 前端定义 `KnowledgeProvider` 接口：`search(keyword, categoryId)` / `list(categoryId, page)` / `detail(id)`。MVP 由 `LocalDbProvider`（查云数据库）实现；若 ima API 可用，新增 `ImaProvider` 按配置切换，**页面层零改动**。
- V1.3 接入云服务 LLM 模块：以检索命中文章为上下文做「装修问答」，以及每周自动生成「本周装修进展摘要」推送。

## 6. 成员权限规格

### 6.1 角色权限矩阵

| 能力 | owner | editor | viewer |
|------|:-----:|:------:|:------:|
| 查看项目全部内容 | ✅ | ✅ | ✅ |
| 写/改日记、材料、花费 | ✅ | ✅ | ❌ |
| 删除自己创建的日记/花费 | ✅ | ✅ | — |
| 删除他人内容 | ✅ | ❌ | ❌ |
| 更新施工阶段状态 | ✅ | ✅ | ❌ |
| 邀请成员 / 改角色 / 移除成员 | ✅ | ❌ | ❌ |
| 项目设置、归档、删除项目 | ✅ | ❌ | ❌ |
| 查看知识库 | ✅ | ✅ | ✅（无需加入项目） |

### 6.2 邀请与加入流程

```
owner/editor 视角（邀请仅 owner 可发）
  project/invite → 选角色 → 创建 invites 记录 → 微信分享卡片
    （路径：pages/join/index?code=XXXXXXXX）
被邀请人
  点卡片 → 微信登录 → join/index 校验 code（有效/未过期/未撤销）
    → 展示项目名与邀请人 → 「接受」→ 写 members（role = invite.role）
    → 跳转项目首页；「拒绝」→ invites.status = revoked
```

- 邀请码默认 72 小时过期；一个码仅可被接受一次；owner 可在成员管理页撤销。
- 已是成员者打开卡片直接进项目，不重复加入。
- **防滥用**：单项目 pending 邀请 ≤ 10 个；members 总数 ≤ 20。

### 6.3 协同编辑规则

| 规则 | 说明 |
|------|------|
| 作者可见性 | 列表与详情展示原作者；被编辑过则追加「xx 最后编辑于 xx」 |
| 编辑入口 | owner 可编辑所有内容；editor 可编辑所有人的内容（家庭场景信任默认放开，靠 revisions 追溯而非锁死） |
| 历史追溯 | 详情页可展开编辑历史（来自 revisions：谁、何时、改了哪些字段） |
| 回滚 | V1 不做 UI 回滚，revisions 保留字段级变更足以人工恢复；V1.x 再评 |

## 7. 实时同步与冲突处理规格

### 7.1 同步模型

**增量拉取为主**：每个项目维度的列表（diaries / materials / expenses / stages / members）在客户端记录 `lastSyncAt`（按集合分开存）。

```
sync(collection):
  请求：where projectId = X AND updatedAt > lastSyncAt（含 deleted = true 的墓碑）
  成功：合并进本地缓存 → lastSyncAt = 本次响应服务器时间
  触发时机：页面 onShow ｜ 下拉刷新（强制全量对比）｜ 写操作成功后
```

### 7.2 实时性分级（降级链）

| 级别 | 机制 | 适用页面 | 说明 |
|------|------|----------|------|
| L1 | 云端实时推送/长连接 | 日记时间线、花费看板 | **运行时验证云服务是否支持实时监听**，支持则启用 |
| L2 | 前台轮询 20s + onShow 立即同步 | 同上（L1 不可用时） | 页面 hide 即停止轮询 |
| L3 | 仅 onShow / 手动下拉 | 成员管理、项目设置 | 低频页面不做轮询 |

**订阅消息**（系统级触达，弥补小程序无法后台推送）：成员可订阅「新日记提醒 / 花费变更 / 阶段更新」，由写操作后的服务端逻辑触发发送。

### 7.3 写冲突处理（乐观锁）

```
编辑页进入：记录 doc.version 为 baseVersion
提交：update ... where _id = X AND version = baseVersion，version + 1
  ├─ 成功 → 追加 revisions 记录 → 本地合并 → 返回详情
  └─ 失败（版本已变）→ 拉取最新版本 → 冲突合并 UI：
        「你的版本」 vs 「对方最新版本」（按字段并列展示）
        → 用户选择「保留我的（覆盖）」或「放弃我的（查看最新）」
        → 图片数组合并策略：并集，按上传时间排序（图文日记极少需逐字合并）
```

- **为什么不用编辑锁**：家庭场景并发编辑是分钟级的偶发，锁会制造「工长占着没退出」的死锁体验；乐观锁 + 冲突 UI 成本最低、最诚实。
- 删除采用软删（`deleted: true`），同步时以墓碑下发，避免「A 删了 B 还看到」。

### 7.4 图片上传

- 选择后本地压缩（短边 ≤1600px，质量 0.8）→ 上传 Storage → 得 fileId 写入文档。
- 约束：单篇 ≤9 张、单张 ≤10MB、仅 jpg/png/webp；不信任客户端文件名，按 `projectId/diaryId/uuid` 生成存储路径。
- 弱网：先落本地草稿（草稿仅存本机，提交成功即清），上传失败可重试。

## 10. 视觉设计规范（双主题，2026-10-06 定稿）

> 设计目标：与业主的家装审美同频（中古风 / 轻奢风），让工具本身也有「家的气质」。
> **定稿：A/B 双主题并存，用户在「我的 → 外观」随时切换**；令牌结构一致，切换只改变量值。

### 10.1 方案 A · 中古暖调（推荐）

| 令牌 | 色值 | 用途 |
|------|------|------|
| `--c-primary` | `#8C5A3B` 胡桃棕 | 主按钮、tabBar 选中、关键操作 |
| `--c-bg` | `#FAF6EF` 奶油白 | 页面背景 |
| `--c-secondary` | `#3F5A4C` 墨绿 | 阶段标签、进度条、辅助强调 |
| `--c-accent` | `#B08A47` 黄铜 | 金额、预算环、星级/标记 |
| `--c-text` | `#3A322B` 深棕灰 | 正文标题 |
| `--c-text-2` | `#8A7E72` | 次要文字 |
| `--c-card-border` | `#E8DFCF` | 卡片 0.5px 细边 |

### 10.2 方案 B · 轻奢冷调

| 令牌 | 色值 | 用途 |
|------|------|------|
| `--c-primary` | `#3E3E42` 炭灰 | 主按钮、tabBar 选中 |
| `--c-bg` | `#F7F7F5` 云雾白 | 页面背景 |
| `--c-secondary` | `#6E7F8D` 雾霾蓝 | 阶段标签、辅助强调 |
| `--c-accent` | `#C2A878` 香槟金 | 金额、预算环 |
| `--c-text` | `#232326` 近黑 | 正文标题 |
| `--c-text-2` | `#8B8B90` | 次要文字 |
| `--c-card-border` | `#E6E6E2` | 卡片细边 |

### 10.3 共用规则（与方案无关）

- **字体**：页面大标题/日记标题用衬线（`font-family: serif`，宋体感，带杂志感）；正文系统黑体 15px / 1.6 行高。
- **圆角**：卡片 20rpx、按钮 16rpx、标签胶囊全圆角；**不用阴影**，靠留白 + 0.5px 细边框分层。
- **金额呈现**：一律金色系（`--c-accent`），预算环/超支提醒同色系加深，不用红绿（避免股票式误读）。
- **阶段状态色**：未开始 `--c-text-2`、进行中 `--c-secondary`、已完成 `--c-primary`；材料状态（待购/已购/已进场）同理递进。
- **图片呈现**：日记图片九宫格 8rpx 圆角、1:1 裁切；票据缩略图 2:3。
- **WXSS 实现**：色值定义为 `app.wxss` 中 `.theme-a` / `.theme-b` 两套 CSS 变量；每页根节点挂 `class="{{theme}}"`，组件只引用变量。
- **主题切换**：入口在「我的 → 外观」；选择持久化到本地存储（key: `theme`，值 `theme-a`/`theme-b`，默认 `theme-a`），启动时读取即时生效；M2 可同步到 `profiles.theme` 实现跨端一致。
