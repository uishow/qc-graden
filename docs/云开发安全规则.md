# 微信云开发 · 数据库安全规则

> 适用环境：`cloudbase-d0gcanr6v1194af27`  
> 配套代码：见 `miniprogram/utils/cloud.js`（数据层适配层）、`miniprogram/utils/write.js`（成员校验写客户端封装）、`miniprogram/cloudfunctions/dataWrite`（成员校验写云函数）、`miniprogram/cloudfunctions/login|init`

## 1. 设计原则

- **读（read）**：装修日记本质是「家庭/好友共享」，业务集合统一放宽为 **所有登录用户可读**，靠应用层 **members 成员关系** 做隔离（见 §6 邀请码授权）。未加入项目的用户虽然在库层面可读，但前端只展示其本人 members 记录覆盖的项目，拿不到别的项目的 `currentProjectId` 也就不会呈现。
- **写（write）**：`diaries` / `expenses` / `materials` 三张内容集合的写权限已收为 **false**，所有增删改统一走云函数 `dataWrite`（管理员上下文，绕过规则），函数内**先查 `members` 确认当前用户是该项目的 active 成员**，不是就拒绝。这样既能支持「家庭成员/协作成员」协同编辑他人条目（推进阶段、改房主记的花费），又彻底堵死被移除成员手机残留 `project_id` 直接越权写入（见 §4）。`stages` / `rooms` 写仍放宽为 `true`（成员可协同推进阶段/房间，二期再收），靠应用层 `members` 隔离。
- **知识库写保护**：`knowledge_articles` / `knowledge_comments` 保持「仅创建者可写」——官方种子文章（云函数写入、无 `_openid`）仍需靠云函数（confirmImaImport / deleteArticle / enrichArticle）操作，不能被任意成员客户端改/删。
- **项目元信息与成员**：`projects` / `members` 保持「仅创建者可写」，其写入（建项目、邀请码重置、移除成员、删除项目）统一走云函数 `joinProject` / `projectAdmin`（管理员上下文，绕过规则）。
- **服务端创建的文档**（云函数写入）不会带 `_openid`，因此 profiles、种子知识文章/分类写权限收为 `false`，只由云函数写。

## 2. 集合级规则（每个集合单独配置）

CloudBase 文档型数据库的安全规则是**按集合单独配置**的：在「云开发控制台 → 数据库 → 点开某个集合 → 权限设置 → 自定义安全规则」里，给该集合粘贴一段 `{"read":...,"write":...}` JSON（不是多集合整段）。每个集合粘贴后「保存」立即生效，无需重部署。

> 误区提醒：旧版「安全规则」高级模式曾支持按集合名分组的整段 JSON（`*-permission` + 各集合名作 key），但现行控制台以「逐集合」为准；逐集合设置最稳妥。

各集合应填的 JSON（`auth.openid` 为微信小程序登录用户；`doc._openid` 为文档创建者，前端写入时自动带）：

| 集合 | read | write | 对应预设 |
| --- | --- | --- | --- |
| projects | true | `doc._openid == auth.openid` | 仅创建者可写，所有人可读 |
| members | true | `doc._openid == auth.openid` | 仅创建者可写，所有人可读 |
| rooms | true | true | 自定义（所有人可读写） |
| stages | true | true | 自定义（所有人可读写） |
| diaries | true | false | 仅 dataWrite 云函数可写（带 members 成员校验）；客户端直写已封死 |
| expenses | true | false | 仅 dataWrite 云函数可写（带 members 成员校验）；客户端直写已封死 |
| materials | true | false | 仅 dataWrite 云函数可写（带 members 成员校验）；客户端直写已封死 |
| revisions | true | `doc._openid == auth.openid` | 仅创建者可写，所有人可读 |
| profiles | true | false | 仅管理端可写，所有人可读 |
| knowledge_categories | true | false | 仅管理端可写，所有人可读 |
| knowledge_articles | true | `doc._openid == auth.openid` | 仅创建者可写，所有人可读 |
| knowledge_comments | true | `doc._openid == auth.openid` | 仅创建者可写，所有人可读 |
| weekly_digests | true | false | 仅管理端（weeklyDigestAuto 定时函数）可写，所有人可读。存定时周报，客户端只读 |
| app_settings | false | false | 仅管理端可读写（存 LLM 密钥，客户端完全不可见；读写走 aiAdmin 云函数） |

即：
- `diaries` / `expenses` / `materials` 用 `{"read": true, "write": false}`（客户端不可直写，写走 `dataWrite` 云函数做成员校验；详见 §4）；
- `rooms` / `stages` 用 `{"read": true, "write": true}`（成员可协同编辑他人条目，二期再收紧）；
- `projects/members/revisions/knowledge_articles/knowledge_comments` 用 `{"read": true, "write": "doc._openid == auth.openid"}`（仅创建者可写）；
- `profiles/knowledge_categories/app_settings` 用 `{"read": true, "write": false}` ——**例外：app_settings 连 read 也要 false**（存 LLM 密钥，客户端直接查询会看到明文密钥；读写一律走 `aiAdmin` 云函数，仅家庭成员可用）。

若控制台提供数据库级的「安全规则」总入口且接受集合名分组 JSON，也可一次性粘贴；但逐集合设置最不易出错。

## 3. 各集合说明与字段约定

| 集合                             | 创建方                          | 写权限       | 关键字段                                                  |
| ------------------------------ | ---------------------------- | --------- | ----------------------------------------------------- |
| projects                       | 客户端                          | 创建者       | `_id`(主键), `budget`(分), `status`                      |
| members                        | 客户端                          | 创建者       | `user_id`(=openid), `project_id`, `role`, `status`    |
| rooms / stages                 | 客户端                          | 创建者       | `project_id`, `sort_order`                            |
| diaries / expenses / materials | 客户端                          | 创建者       | `project_id`, `version`(乐观锁), `image_paths`(fileID[]) |
| revisions                      | 客户端                          | 创建者       | `project_id`, `collection`, `doc_id`, `prev_version`  |
| profiles                       | 云函数 login                    | 不可写       | `owner_id`(=openid), `nick_name`                      |
| knowledge_categories           | 云函数 init                     | 不可写       | `key`, `name`, `sort_order`                           |
| knowledge_articles             | 云函数 init（官方）/ 客户端（成员导入，V1.3） | 创建者（成员导入需客户端可写） | `scope`, `category_id`, `status`, `view_count`        |
| knowledge_comments             | 客户端                          | 创建者       | `article_id`, `owner_id`, `content`                   |

## 4. 已知权衡（需确认）

- **邀请码授权（2026-10-09 新增）**：项目授权走应用层 `members` 表 + `projects.invite_code_family` / `invite_code_member` 两种 6 位永久码。家庭成员码加入得 `family`（全部权限），协作码加入得 `member`（仅协同编辑）。管理员（owner/family）可在「我的」页管理面板重置邀请码、移除成员、退出/删除项目（均经 `projectAdmin` 云函数）。
- **协同编辑 + 成员校验写**：`diaries` / `expenses` / `materials` 的写权限已收为 `false`，所有增删改改走云函数 `dataWrite`（`miniprogram/cloudfunctions/dataWrite/`）。该函数在管理员上下文执行（绕过安全规则），但在落库前**先查 `members` 表确认 `user_id==OPENID && project_id==目标项目 && status=='active'`**，非 active 成员直接拒绝（返回 `code:'NO_MEMBER'`）。这既保留了「家庭成员/协作成员可改他人条目」的协同能力，又堵死了「被移除成员手机仍残留 projectId、直接 add/update」的越权写入漏洞（2026-10-09 实测：已移除成员 M13… 仍写 '999' 日记 + '777' 花费，根因就是写规则为 `true`）。
  - 客户端调用封装在 `miniprogram/utils/write.js`（`write.insert/update/remove`），返回形状与 `utils/cloud.js` 一致（`{ data, error }`），各编辑页只改了写调用、读逻辑不动。
  - insert 时服务端**强制覆盖 `project_id`**，防止客户端把内容写进别的项目；update 支持可选乐观锁 `version`（与编辑页既有 `version` 逻辑一致，老数据无 version 则按 `_id` 直接更新）。
  - `stages` / `rooms` 写仍 `true`（协同推进阶段/房间），属二期待收紧项；现阶段靠应用层 `members` 隔离缓解。
- **知识库仍受保护**：`knowledge_articles` / `knowledge_comments` 保持「仅创建者可写」，官方文章与成员导入的确认/删除走云函数，成员不能客户端改/删他人文章。

## 5. 与适配层的关系

`utils/cloud.js` 的写入链 `update(o).eq('id',x).eq('version',v)` 命中 `stats.updated===0` 时返回 `conflict` 错误，前端据此弹「内容已被他人修改」。安全规则只决定「能不能写」，乐观锁决定「并发写谁赢」，二者互补。
