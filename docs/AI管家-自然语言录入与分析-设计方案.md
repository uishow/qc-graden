# AI 管家 · 自然语言录入与多维分析 设计方案

> 整理范围：从「针对 AI 管家的要求如下…先给出方案设计」起，到 2026-10-15 全部问答的
> **需求 → 方案 → 迭代 → 最终架构 → 决策依据**的完整记录。
> 项目：装修日记本（微信原生小程序 + 腾讯云开发 CloudBase）
> 环境：`cloudbase-d0gcanr6v1194af27`

---

## 0. 一句话总结

需求是「用说话的方式录入数据、用说话的方式做统计分析」。
实现过程中发现真正的问题不是"AI 不够聪明"，而是**架构把模型放错了位置**——用有限规则去挡无限表达。
最终方案是**混合渐进路线**（LLM 优先 + 规则兜底 + 预览卡拦截）+ **反馈闭环**（把千奇百怪收敛成可排序的 Top 清单）+ **回归语料**（压住旧病复发）。

## 1. 原始需求

> **问**：针对 AI 管家的要求如下：
> 1、能使用自然语言，录入系统相关的录入功能，比如：日记、花费等。
> 2、能使用自然语言，对程序体中的相关数据进行多维度分析、统计等。**先给出方案设计。**

## 2. 初版方案设计（原文要点）

### 2.1 总体架构

在 `pages/ai/assistant.js` 的 `send()` 里、LLM 调用**之前**插入**意图分发器（dispatcher）**：

```
用户自然语言
   │
   ├─ 录入意图（材料 / 日记 / 花费）
   │     └─→ 本地启发式解析器 tryParseXxx(text)
   │           └─→ write.insert(collection, projectId, data) → dataWrite（已有成员校验）
   │                 └─→ 返回结构化成功文案（不走 LLM，离线可用）
   │
   └─ 分析 / 查询意图（统计 / 趋势 / 进度）
         └─→ 查询路由：正则识别常见问法？
               ├─ 是 → 客户端 computeStats 真实聚合 → 格式化统计文本（离线可用）
               └─ 否（开放式）→ 聚合结果 + 增强快照 发 aiAssistant，LLM 基于真实数字叙述
```

落库全部复用现有 `dataWrite` 云函数（含 active 成员校验），**不新增云函数**。

### 2.2 功能 1：自然语言录入

| 解析器 | 提取字段 | 说明 |
|---|---|---|
| `tryParseIntakeMaterial` | 名称 / 品牌 / 数量 / 单位 / 单价 / 备注 | 已完成 |
| `tryParseDiary`（新增） | 日期 / 房间 / 标题 / 正文 | 日期支持「今天/昨天/前天/上周X」或「10月15日」；标题取首句 ≤20 字 |
| `tryParseExpense`（新增） | 金额(分) / 类型 / 支付日期 / 阶段 / 备注 | 类型：`人工/设计/订金` → labor/design/deposit，其余 other |

**房间 / 阶段名匹配**：依赖项目已知的房间名 / 阶段名做包含匹配（`客厅`→"客厅"、`水电`→"水电改造"），
匹配不到就留空或进备注——保证写进 `room_ids`/`stage_ids` 的是**真实存在的 id**，不写脏引用。

**字段对齐现有落库结构**（已核实）：
- 日记：`title / content / diary_date(YYYY-MM-DD) / room_ids[] / stage_ids[] / attachments / version`
- 花费：`amount(fen) / type(labor|design|deposit|other) / pay_date(YYYY-MM-DD) / stage_ids[] / remark / attachments / version`

### 2.3 功能 2：自然语言多维分析

**现状问题**：`aiAssistant` 发给 LLM 的 snapshot 是**聚合后**的，复杂精确查询（按月趋势、某房间占比、平均月花）LLM 易算错、易瞎编。

**增强**：客户端用 `buildSnapshot` 已持有的全量 `expenses`/`materials`/`diaries` 做**真实聚合**（`computeStats`）：
- 花费：总额 / 本月 / 按类型 / 按阶段 / 按房间 / 按月趋势
- 材料：总数 / 待购金额 / 已购金额 / 按房间 / 按状态
- 进度：各阶段状态分布 / 当前进行中 / 滞后预警
- 综合：预算执行率（计划 vs 已花）

**查询路由**：正则命中常见问法 → 直接返回格式化统计文本（**离线也能用**）；
开放式问题 → 聚合结果 + 增强快照发 LLM，让它基于**真实数字**叙述而非估算。

### 2.4 实施阶段

1. 阶段一：录入-花费 + 录入-日记（启发式解析，复用材料通道）
2. 阶段二：查询路由 + `computeStats` + 正则快查（离线可用）
3. 阶段三（可选）：自由文本录入接 LLM 兜底提取 + 快照增强

### 2.5 待确认的两个策略（用户回复）

| 策略点 | 用户选择 |
|---|---|
| 录入解析 | **启发式 + LLM 兜底**（后来升级为 LLM 优先） |
| 分析查询 | **客户端聚合 + 正则快查** |
| 整体路线 | **全都要 · 渐进混合**（三条路线都做，分期落地） |

## 3. 迭代全记录（问答 → 根因 → 修法）

### 3.1 「材料录入通道不可行，发送后死机」

- **根因**：`send()` 里裸调 `tryParseIntakeMaterial` 抛 `ReferenceError`，`loading` 永不复位 → UI 假死。
- **修法**：`send()` 整体包 try/catch + 统一 `finish()` 收尾函数，**任何路径都复位 loading**。
- **沉淀为原则**：不卡死、不静默失败（见 §8 三条底线）。

### 3.2 「bug 已修复，但数据未对应到相应字段」

- **根因**：写入字段与集合读取端不一致（材料备注应是 `remark` 不是 `note`；缺 `created_at`/`updated_at`/`deleted:false`/`version`）。
- **修法**：逐类对齐字段（材料 / 花费 / 日记），`dataWrite` 透传 `event.data`，**字段名 100% 由前端负责**。
- **后续隐患**：阶段 / 房间 id 静默丢失（见 §3.6 大坑）。

### 3.3 「品牌解析不出来 / 无法录入日记 /『本月花费多少』无法识别」

| 问题 | 根因 | 修法 |
|---|---|---|
| 品牌解析错 | ① 属性词当品牌（「实木地板」→ brand=实木）② 不支持显式声明 | 新增 `MAT_ATTR_WORDS` + `stripAttr()`；支持 `品牌是X / 品牌：X / 牌子X / X牌`；`MAT_TYPE_KEYWORDS` 长度降序 |
| 录入日记不生效 | `detectIntent` 先判 `hasMat`（含「录入」）再判 `hasDiary` | `hasDiary` **提到 `hasMat` 之前**；加 `(?!本)` 负向前瞻避免「日记本」误判 |
| 「本月花费多少」无响应 | 含「花费」被判成录入 | 查询路由**优先于录入意图** |
| 输入看不全 | 单行 `<input>` | 换 `textarea auto-height maxlength=500` |

### 3.4 「这些模型是不是要不断的训练呢？」

- **当时的回答**：不需要训练。走的是**固定正则规则 + 预训练大模型 API**，改规则就是改代码。
- **后来修正得更准确**（见 §4）：模型确实不用训练，但**"不是训练问题"不等于"没问题"**——真问题是架构把模型放错了位置。

### 3.5 五问题一轮（截图）

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 户型图调不出来 | 动词表缺「调出来」，落到 LLM 问答（AI 看不到附件本体只能编） | 补齐动词表；问答上下文标注「📷有附件」并引导说调图指令 |
| 2 | 无法修改装修进度 | 查询路由把「把进度修改为…」抢走当进度查询 | 新增 `_parseStageUpdate`，**排在 `_routeQuery` 之前** |
| 3 | 录入花费变成材料录入 | 「录入」命中材料触发词，材料判定在前 | 花费意图提前；支持「费用是200」「主要内容是…」当备注 |
| 4 | 日记标题 / 内容不识别 | 无显式声明解析 | 支持「标题是X / 标题：X」「内容是X / 内容：X」 |
| 5 | 表单输入框显示不全 | 微信 `input` 只给 padding 不设高，内容区被压扁 | `.form-input` 显式 `height:80rpx + line-height:80rpx` |

**同时修掉的回归隐患**：「瓷砖 10块」的「块」不再被当钱；「块钱」必须排在「块」前面匹配。

### 3.6 二轮 + 三轮（截图）

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 录入框还是一行 | `auto-height` 初始太矮 | 默认 3 行（132rpx），最多 6 行 |
| 2 | 花费卡按钮丑 | 三按钮挤一行 | 经典布局：「修改」挪到标题右侧小链接，底部只留「取消 \| 确认写入」 |
| 3 | 进度推进按钮不全 | **我的真 bug**：阶段卡漏渲染确认按钮 | 统一所有卡片的双按钮布局 |
| 4 | 备注被切碎（「录入 是 师 的 钱」） | 备注剥离把「设计师」「定金」等领域词也删了 | 保留领域词，只剥语气词 |
| 5 | 「999楼项目日记」附件调不出 | 2-gram 里「999」被稀释成「99」，「日记」因 df 太高被过滤，score=1 < 阈值 2 → 落 LLM 编话 | 数字串强信号 +3；**选篇失败不再丢给 AI**，改给引导列表 |

> **大坑（Phase 2/3 期间挖出）**：`buildSnapshot()` 返回两套结构——`snapshot`（发 LLM 的精简版）里 rooms/stages **只有 `name`、没有 `id`**；带 `id` 的原始数组在 `raw`。
> 有 4 处把 `snapshot` 当 id 源用（`_matchStageIds`/`_matchRoomIds`、`_adaptLLMData` 名字→id、`_entryRows` id→name），
> 全部拿到 `undefined` → **阶段/房间关联静默丢失**，写进库了但页面读不到。
> 已统一改读 `raw`，抽出 `_knownStageNames()`/`_knownRoomNames()`。
> **测试桩此前给 `snapshot` 塞了 id，把这个 bug 完全掩盖**——已把桩改成还原真实形状。

### 3.7 「每次 AI 问答都出现不同问题，周而复始，如何彻底解决？」

→ 这是本次最重要的一次问答，完整分析见 §4。

### 3.8 「顺着 AI 的引导说了，但又出不来结果」

- **已解决的一半**：我们自己代码生成的引导 → 改成**可点按钮**，不用重打；带项目名、说清失败原因。
- **补上的一半**：**AI 自己用自然语言给的引导**（大模型自由发挥的「你可以试试说…」）——
  现在会把回答里引号包着的示例指令自动抓出来变成**可点 chips**：
  - 含指令动词的（显示/查看/录入/记一笔/把…改为/设为…）→ 原样成按钮
  - 《X》且 X 确实是项目里的日记标题 → 自动补成「显示《X》的附件」
  - 无关引号词不做按钮，最多 3 条

### 3.9 「录入完之后不用再跳转了」

- 删掉三处跳转调用和 `_afterEntryJump` 方法本体
- 回执从「即将跳到「花费」页」改成「可在「花费」页查看这笔记录」
- 加回归断言：**三类录入后 `switchTab` 次数必须为 0**，防止以后又被加回去

### 3.10 「反馈记下来之后要如何处理？」/「哪些问题该进反馈闭环？」/「全做」

→ 完整设计见 §5、§6。

## 4. 关键认知转折：为什么"周而复始"

### 4.1 两类 bug 性质完全不同

| 类别 | 性质 | 例子 | 会不会一直冒出来 |
|---|---|---|---|
| **A 类 · 理解类** | **结构性**：中文说法近乎无限，规则有限 | 「调出来」「999楼」「设计师的定金」「标题是X」 | **会，永远会有新说法** |
| **B 类 · 实现回归类** | 测试缺口，跟自然语言无关 | 按钮漏渲染、id 映射丢失、快照卡恒显示"尚未设置" | 不会，靠回归测试压住 |

更糟的是：**每补一条规则就多一处回归风险**（「块」是钱还是量词？「块钱」和「块」谁先匹配？）。

### 4.2 修正"不是模型训练的问题"

模型**不用训练**（用现成大模型 API，能力够用）。
真正的问题是**架构把模型放错了位置**：规则在前面硬扛，模型只在规则失败时才兜底——
等于用**有限规则**去挡**无限表达**，而最擅长理解任意说法的模型只当备胎。**这才是周而复始的根本原因。**

### 4.3 彻底解：三层

| 层 | 做什么 | 解决什么 |
|---|---|---|
| **架构层** | 让模型做"理解"，规则降级为：① 离线兜底 ② 结果校验修复；写入必经预览卡 + 修改表单；查不到就给**选择器列表**，绝不让 AI 编理由 | 新说法自动被覆盖；理解错也不落脏数据 |
| **数据层** | 自动采集「没帮上忙」的信号，按频次排序 | **把"千奇百怪"收敛成一张 Top 20 高频清单**——唯一能把无限变有限的机制 |
| **工程层** | 修一个 bug = 补一条回归用例；改解析规则 = 跑全量回归 | 压住 B 类回归 |

**写入必经预览卡**的价值常被低估：即使理解错了，数据也不会脏（点「修改」改一下即可）。
真正危险的是**读/查询类**没有这道防线（AI 编"图片已过期"），所以这类必须改成"查不到就给选择器"。

### 4.4 用户选择的执行顺序：3 → 4 → 2 → 1

| 顺序 | 事项 | 状态 |
|---|---|---|
| 3 | 录入链路改 LLM 优先，规则降为兜底 | ✅ |
| 4 | 查询类统一"选择器"模式 | ✅ |
| 2 | 👎 反馈闭环 + 高频清单 | ✅ |
| 1 | 测试语料入库 + "修 bug 必补用例"约定 | ✅ |

## 5. 最终架构（现状）

### 5.1 意图路由顺序（`send()` 内固定，顺序不能变）

```
1. _parseStageUpdate   「把 X 阶段改为进行中」
   └─ 必须排在 _routeQuery 之前：否则「把…装修进度修改为…」会被当进度查询抢走
2. _routeQuery         统计问答 → 客户端 computeStats 真实聚合
3. _isDiaryLookup      「显示《X》的附件」→ 查库 + 2-gram 选篇 + createSignedUrls
4. detectIntent        录入意图（材料 / 花费 / 日记）
   ├─ LLM 优先：_llmParse（云函数 mode:'parse'，一次判意图 + 抽字段）
   └─ 规则兜底：_tryParse（离线可用）；置信度不足才调 _llmExtract
5. 开放式问答          聚合结果 + 增强快照 → aiAssistant → LLM 基于真实数字叙述
```

### 5.2 LLM 优先（`aiAssistant` 云函数 `mode:'parse'`）

- **一句话同时判意图 + 抽字段**。此前最坑的是"意图判错 → 用错模板"（录入花费被判成材料）。
- 规则降级为**离线兜底**（模型没配 / 调用失败时仍可用），每条路径独立降级，互不影响。
- 云函数侧 `repairParse()` 做校验修复：阶段/房间名过滤到已知列表、status 限定 pending/doing/done、关键字段缺失返回 null **不落脏数据**。

### 5.3 防脏数据三道闸

1. **预览确认卡**（Phase 1）：解析成功先弹字段卡，确认才落库
2. **半屏编辑表单**（Phase 3）：点「修改」预填解析结果，改完再落库；必填为空**不关表单**
3. **校验修复层**（云端）：缺关键字段直接返回 null

### 5.4 查询类：绝不编理由

- 查不到那篇日记 → 返回**引导列表**（最近 5 篇带 📷 附件数）+ **项目名** + 可点 chips，
  **不再返回 null 落 LLM 问答**（AI 看不到附件本体，只会编"调不出来/图片过期"）
- 没附件 → 明确说"确实没有存附件（须在日记页上传）"
- 链接失败 → 带上具体错误原因

### 5.5 文件清单

| 文件 | 职责 |
|---|---|
| `miniprogram/pages/ai/assistant.js/.wxml/.wxss` | 助理页：路由、解析、预览卡、表单、chips、👎 |
| `miniprogram/cloudfunctions/aiAssistant/index.js` | `mode:'parse'`（理解 + 抽取）、`mode:'extract'`、`repairParse/repairExtract`、快照增强 |
| `miniprogram/cloudfunctions/aiFeedback/index.js` | 反馈闭环：`log/list/setStatus/summary` + 项目级门禁 |
| `miniprogram/utils/aiFeedback.js` | 客户端封装，**失败静默** |
| `miniprogram/pages/ai/feedback.js/.wxml/.wxss/.json` | 管理员待办台 |
| `miniprogram/pages/user/profile.js/.wxml` | 「我的」页入口 + 待办角标 |
| `tests/ai-assistant.harness.js` | 135 条：解析 / 意图 / 录入 / 反馈埋点回归 |
| `tests/ai-feedback.harness.js` | 19 条：云端权限门禁 / 项目级隔离回归 |

## 6. 反馈闭环设计（数据层）

### 6.1 记录什么（字段）

| 字段 | 说明 |
|---|---|
| `question` | 用户原话（最关键，用来复现） |
| `understood` | AI 当时的理解（意图 + 抽出的字段） |
| `fixed` | **用户改后的正确答案**（`edit_diff` 专用） |
| `reply` | AI 的回复（判断是否编造） |
| `signal` / `intent` / `norm` / `reason` | 信号类型 / 意图 / 归一化 key / 差异字段名 |
| `project_id` + `created_at` | **不记任何身份信息** |
| `status` + `note` | 待处理 / 已修复 / 不是问题 / 已忽略 + 处理备注 |

### 6.2 信号清单（自动采集为主，不靠用户举报）

| # | 信号 | 触发时机 | 权重 |
|---|---|---|---|
| 1 | `edit_diff` | 用户点「修改」改了字段后落库，对比 AI 原解析 vs 用户改后 | **100** |
| 2 | `unparsed` | 判定是录入但抽不出字段，走了兜底提示 | 80 |
| 3 | `thumb_down` | 用户点 👎 | 60 |
| 4 | `no_result` | 查询落空（查不到那篇日记） | 50 |
| 5 | `retry` | 同一件事重问 | 30 |
| 6 | `cancel` | 用户在预览卡点「取消」 | 20 |
| 7 | `degraded` | AI 降级回答（未配置 / 调用失败） | 10 |

**第 1 条价值最高**：用户每次在预览卡上改字段，系统就已经知道"AI 理解错了什么、正确答案是什么"——
这是免费的**高质量标注**，比让任何人写反馈都准。

**判定边界**：`edit_diff` 只在用户**真的改了字段**时才记；不改直接确认 = 解析正确，不记（否则全是噪声）。

**`retry` 阈值**：2-gram 重合率 **≥0.8** 且长度比 ≥0.6。
（0.6 会把「水电阶段花了多少 / 木工阶段花了多少」误判成重问，污染清单。）

### 6.3 不进闭环的（排除噪声）

正常录入并点确认（成功路径）· 纯问答且没点踩 · 用户自己删改输入框 · 闲聊

### 6.4 进入后如何判断"值不值得修"

1. **聚合**：按 `signal | intent | norm`（归一化：去标点 + 数字变 `#` + 截 24 字）合并计数。
   **单次失败可能只是用户表达问题，重复出现才是真问题**。
2. **排序**：出现次数 × 信号权重，最痛的排最前。经验规律：**修掉前 5 个高频说法通常覆盖 60% 以上失败**。

### 6.5 三类问题，三种处置（关键：分流）

| 类型 | 怎么判断 | 谁处理、怎么动 |
|---|---|---|
| **A 理解错** | AI 懂错了意图或字段 | **我处理**：补规则 / 调提示词 + **把这条原话加进测试语料**（永久防复发） |
| **B 数据/权限类** | 跨项目查不到、日记没存附件、字段没写进去 | **产品缺陷，不是 AI 问题** → 单独排队给用户决策 |
| **C 期望超出能力** | 用户要的功能系统根本没有接口 | **记成需求，不是 bug** → 进需求池，不占 AI 修复时间 |

**分流的价值**：很多"AI 问题"其实属于 B（跨项目找日记）和 C（要 AI 直接看图片内容）。
把它们摘出来，AI 的问题清单会一下子干净很多。

### 6.6 严重度分级

| 级别 | 情形 |
|---|---|
| **P0** | 字段/金额错——**会造成脏数据** |
| **P1** | 完全没结果（查不到、没看懂） |
| **P2** | 理解有偏差，用户小改一下能用 |
| **P3** | 期望超出能力 → 转为需求 |

### 6.7 后台与运营节奏

- **入口**：「我的 → AI 管家反馈」（仅管理员）+ 待处理类数角标
- **状态机**：待处理 → 已修复 / 不是问题 / 已忽略，**整组标记**（同类说法只处理一次），可恢复待处理，已修复可写备注
- **「📋 复制待办」**：导出「原文 + 差异字段 + AI 解析 + 用户改后答案」，直接贴给开发/AI 批量修
- **每周 30 分钟**：拉 Top 20 → 判定 A/B/C → A 类直接修 + 补用例 → B/C 整理成需求清单
- **三个度量**：👎 率（点踩数/总问答数）· Top 10 占比 · 平均修复周期

### 6.8 两个必须避开的坑

1. **别让用户填表** —— 一个 👎 就够，一填表反馈率就掉到接近 0
2. **别只收集不处置** —— 必须有状态机，否则三个月后就是一堆没人敢删的数据

## 7. 数据模型与权限

### 7.1 `ai_feedback` 集合

| 项 | 值 |
|---|---|
| 安全规则 | `{"read": false, "write": false}`（**read 也要关**：含用户原话 + AI 回答，属隐私） |
| 读写入口 | 只能经 `aiFeedback` 云函数 |
| 索引 | `created_at` 降序（翻页）、`status` 升序（summary）、`project_id` 升序（隔离） |

### 7.2 项目级隔离（2026-10-15 收紧）

```
members 表：user_id == openid  且  status == 'active'  且  role ∈ {owner, family}
        → 得到「我管理的项目 id 集合」
        → list / summary / setStatus 全部按 project_id ∈ 该集合 过滤
```

| 角色 | 中文 | 能看 |
|---|---|---|
| `owner` | 管理员 | ✅ 自己担任管理员的项目 |
| `family` | 家庭成员 | ✅ 同上 |
| `member` | 协作成员 | ❌ 入口都不显示 |
| 已退出（`status='left'`） | — | ❌（即使 role 仍为 owner/family） |

**`setStatus` 也必须带项目条件**——否则整组标记会把别的项目同 `signal|intent|norm` 的行一起改掉（越权写入）。

## 8. 三条底线（做不到零问题，但必须守住）

1. **不写脏数据**（预览卡 + 表单 + 校验修复层兜底）
2. **不卡死、不静默失败**（`loading` 必复位）
3. **不确定就说不确定并给选项，绝不编造**（查不到给选择器，不编理由）

守住这三条之后，剩下的都只是"理解不够准"，用户改一下即可，**不会污染数据、不会崩**。

## 11. 踩过的坑（附录）

| 坑 | 症状 | 原因 / 修法 |
|---|---|---|
| **`snapshot` 没有 id** | 阶段/房间关联静默丢失，写进库页面读不到 | `snapshot` 是发 LLM 的精简版（只有 `name`），带 `id` 的在 `raw`。所有名字↔id 映射必须走 `raw` |
| **快照卡恒显示"尚未设置"** | 展示字段读错对象 | 展示文本在 `snapshotView`，不在 `snapshot` |
| **裸调 Page 方法** | 抛错后 `loading` 永不复位 → 假死 | 必须 `this.xxx`；`send()` 整体 try/catch + `finish()` |
| **`visibleWhere` 写成 `async`** | 项目隔离**一行都挡不住**，且初看能跑 | `where(一个 Promise)` → `Object.keys(promise)` 为空 → 条件全命中。**拼 where 条件的辅助函数必须同步** |
| **`limit(500)` 一把拉** | 反馈一多只统计到前 100 条（静默少算） | 改 `fetchAll` 分页（100/页，最多 10 页） |
| **`retry` 阈值 0.6** | 「水电阶段花了多少 / 木工阶段花了多少」误判重问 | 提到 0.8 + 长度比 ≥0.6 |
| **`_lastUserText` 未赋值** | 👎 回填不到用户原话 | 必须在 `send()` 开头赋值 |
| **测试用 `/tmp` 临时副本** | 反向拷贝覆盖了 mock，导致用例误判 | 仓库内 `tests/` 是**唯一真源** |
| **`app_feedback` 的 `.order()`** | 报 not a function | 改拉全表 + JS sort；新集合第一时间建 `created_at` 索引 |
| **自定义 tabBar 盖住弹窗** | 弹窗按钮被遮 | `.mask` z-index 99999 + 弹窗期 `getTabBar().setData({hidden:true})` |
